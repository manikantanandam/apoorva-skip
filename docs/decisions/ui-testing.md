# UI testing

## Decisions
- **Target:** `ApoorvaUITests` (XCUITest bundle) in `app/Darwin/Apoorva.xcodeproj`, sources in `app/Darwin/UITests/`. Added as a Testable to the `Apoorva App` scheme.
- **Layout for growth:** one folder per feature (`UITests/Login/`), page objects in `UITests/Support/Screens/`, shared `AppLauncher` and `AccessibilityID`. Add new screens/modules the same way.
- **Stubbed auth:** launch arg `-UITesting` (DEBUG only, `UITestingConfig` in ApoorvaAppCore) swaps `ServicesContainer.authService` for `FakeAuthService` (ApoorvaServices), skips `FirebaseApp.configure` in `onInit()` and wipes UserDefaults. Credentials: `uitest@apoorva.app` / `UITest@123`.
- **Identifiers:** added at call sites in `AuthScreens.swift` (not in ManiSwiftUIComponents, to avoid a library release). Strings live in `ApoorvaModules/Onboarding/AccessibilityID.swift` and are mirrored in `UITests/Support/AccessibilityID.swift`; keep both in sync.
- **Runner:** `scripts/ui-test.sh [Class[/method]]` (separate from `build.sh`, which only handles `libraries/*`).

## CI
- UI tests run only on pushes to main, not on pull requests. `.github/workflows/ui-tests.yml` holds the job (macos-15, iPhone 17; runs `scripts/ui-test.sh`; uploads the log and xcresult on failure); the `ui-tests` job in `ci.yml` calls it with `if: github.event_name == 'push'`. Caveat: if `UI Tests` is a required check, a job skipped on PRs may block merges.
- To verify the UI tests on a branch without merging, run the "UI Tests" workflow manually (Actions tab, "Run workflow", pick the branch). The optional `test` input filters like the script: `LoginUITests` or `CustomerListUITests/testCustomerList`; empty runs everything. It is independent of the Sonar flow.
- It runs unconditionally (not module-filtered) because the app depends on every library. Add it as a required check in branch protection if wanted.

## Feature tests (POS, customer picker)
- **Demo mode was removed (2026-11-20)** (`DemoSeeder`, `AppSession.isDemo`, `DemoShopView`, `setDemoUser`). The UI tests below that enter via the demo shop (`HomeScreen.enterDemoShop`, `POSUITests`, `CustomerPickerUITests`, `KiranaPOSUITests`) no longer have an entry point and need a new offline seeded entry (e.g. a `-UITesting` seed) before they can run.
- (Obsolete) Entry point is the demo shop: Splash "See a demo shop" -> "Try sample shop" (fancy vertical) -> "New bill" button. It seeds local SQLite only, so no Firestore/auth is needed. `HomeScreen` page object wraps this.
- New files must be registered by hand in `Apoorva.xcodeproj/project.pbxproj` (explicit file refs, no synchronized folders).
- The fancy POS is a quick-items grid (buttons labelled by item name), not a search list.
- Screens under a full-screen cover (New bill) leave Home in the accessibility tree, so static-text lookups like "Ravi Kumar" also match Home's recent bills. Use the picker's row button label (`", Name, "`) instead.
- Demo seeding is async and the local DB persists between launches, so the picker can open before customers exist. `CustomerPickerUITests.setUp` reopens the picker until the seeded customers show.
- Picker tests cover the focus rules: search focus hides the new-customer form and Recent; phone/name focus hides search, list, Recent and the bottom bar; submitting Name restores everything.
- Tapping a tile does not add to the cart: it opens the add-line half sheet (MRP, quantity, "Add to bill"), so the cart fills only after confirming. `POSScreen.addItem(named:)` does both steps.
- `POSUITests` now also covers add/edit/remove lines, quantity clamp, Find, quick item, bill discount (incl. manager PIN), hold/resume, checkout (credit blocked for walk-in, change due, split, hold), cash sale -> receipt -> new bill/home. POS identifiers (`AccessibilityID.Pos.*`, `QuickAddLine.*`) are set in `QuickGridPOSView`: toolbar buttons, More menu, Find, checkout, tiles (`pos.tile.<name>`), cart lines, MRP/discount fields, stepper, save/remove. Written without a simulator run: the discount-sheet "Percent" label, Split chip and cart-line tap target still need verifying with `scripts/ui-test.sh POSUITests/<method>`.
- Checkout tests (in `POSUITests`) cover card, UPI (pay screen, mark received, change mode, back), credit with/without customer, changing customer from checkout, discount/two-item totals, cash received/change, split (partial, full, cash+UPI, credit warning) and post-sale reset. Customer-creation tests (in `CustomerPickerUITests`) cover phone/name validation (9/10/11 digits, spaces, letters, blank/whitespace name), duplicate phone reuse, trimming, search edge cases and switching customers. All unrun: verify `splitSegment`, the keypad digit buttons and the phone prefill-from-search test first.
- `KiranaPOSUITests` runs against the kirana sample shop (`HomeScreen.enterDemoShop(sampleShop: "Sri Lakshmi Stores")`): weighed item "Onions (kg)" (weight sheet, presets, by-amount) and variant item "Tea Powder 250g". `DemoSeeder` now seeds sizes 100g/250g/500g on that one kirana item (`variantsJSON`) because no demo item had variants. Ids: `WeightSheet.*`, `VariantSheet.*`. Unrun; assumptions to check: sample-shop option is a button whose label contains the shop name, preset chip labels ("1 kg", "250 g"), and that the cart line shows "/kg" and the chosen size as static text.
- Bill discount mode segments are labelled "₹ amount" and "%" (not "Percent"). The demo has no manager PIN, so only the wrong-PIN path is testable ("That PIN isn't a manager's. Try again."). Close with items shows a confirmation dialog (Hold bill / Discard bill / Keep billing); `POSUITests` covers it plus undo-after-sale (skips if the role can't undo).
- Debugging: run one test (`scripts/ui-test.sh Class/method`), not the whole bundle.
- CI: the app target bundles both gitignored Firebase plists, so the `ui-tests` job runs `scripts/setup-firebase-config.sh` from repo secrets first. Without it the build fails ("Build input file cannot be found: GoogleService-Info-production.plist", PR #80).

## Seeded launch (2026-11-21)
- **Entry point:** `-UITesting -UITestingSeed fancy|kirana` (`AppLauncher.launchSeeded`) replaces the removed demo shop. `UITestingConfig.seedVerticalName` is DEBUG-only; `UITestSeeder` (ApoorvaAppCore) is wrapped in `#if DEBUG`, so release builds contain none of it.
- **Data integrity:** `ServicesContainer` swaps in `FakeUserService`, which emits nothing until the seeder finishes. The seeder writes settings, items, customers and sales while the session has no org, so `OrgCollectionRepository`/repositories write local-only and never touch Firestore, then publishes the owner (org `uitest-org`). Production auth/profile/org flows are unchanged and only reachable without the seed argument.
- **Fixture:** Ravi Kumar, Meena S (₹1,120 due), Sneha P, Anil Regular (6 visits = Regular), Kavya New (created today, no visits). Customer aggregates are fixed values, not derived from the seeded sales.
- **Customers list:** `UITests/Customers/CustomerListUITests.swift` + `CustomerListScreen` cover header, rows/badges, search, filters, add customer, detail, long-press actions, More menu. Only new identifier: `customers.moreMenu`. Written without a simulator run; verify first: `UITestSeeder` compiles (Customer/Sale/AppUser inits), Home reaches `waitForSeededHome`, the clear-search key-delete test, long-press menu buttons, and form placeholders ("Anitha Rao", "+91 97010 55443").
- **Follow-up:** `POSUITests`, `CustomerPickerUITests` and `KiranaPOSUITests` still call `enterDemoShop`; switch them to `launchSeeded` (kirana ones to `launchSeeded(vertical: "kirana")`; the kirana seed has no `variantsJSON`, so the Tea Powder variant tests still need it).

## One test per screen
- Each UI test class has a single `testX()` that runs named scenarios through `XCTContext.runActivity`, so the app launches and seeds once per class (a launch per test dominated run time). A `scenario(_:_:)` helper resets to a known screen first; scenarios that change data (add customer, hold bills, complete sales) run last.
- All classes now use `launchSeeded` (the old `enterDemoShop` is unused). `UITestingConfig.isEnabled` swaps `NoOpCustomerService`, `NoOpSaleService` and `NoOpHeldBillService` into `ServicesContainer`, because a seeded owner has an org and the real services would write to an unconfigured Firestore (sales and holds fail otherwise). `UITestSeeder` gives kirana "Tea Powder 250g" sizes so the variant sheet opens.
- Device quirks: swiping a sheet down doesn't dismiss it (tap its Close); the centre of cart-line and held-bill rows doesn't take taps (tap the left side); a customer row's accessibility label must start with the name (CustomersView sets it explicitly).
- Not covered: kirana weighed-line edit; POS More-menu, bill-date, manager-PIN and "Apply disabled" checks; checkout credit/split/cash-change (checkout was redesigned in #95 with per-mode amounts, no split screen). Card and UPI sales type the full amount, since nothing typed means all cash.
- While debugging a failure, comment out the scenarios that already passed and leave a "resume here" marker; restore them before the final full run.
- `scripts/ui-test.sh` passes `-allowProvisioningUpdates` so a physical-device run can regenerate the runner's profile.

## Known risks
- Fixed: `FirebaseApp.configure()` never runs in `-UITesting` mode, so Firebase handles crashed (`FIRIllegalStateException`). Two fixes:
  - `FirebaseFirestoreStore` resolves Firestore lazily via `database()`, which throws when `FirebaseApp.app() == nil`; `listen` then emits one `nil` (missing doc) so the session still resolves (-> onboarding). Never capture an SDK handle at init.
  - `FakeRemoteConfigService` (serves catalog defaults only) replaces the Firebase one in `ServicesContainer` when `UITestingConfig.isEnabled`. Without the defaults, flags read false and the onboarding flow broke.
- Other Firebase-backed services (Analytics, Crashlytics, Remote Config, Firestore) are not stubbed; if one is touched before login in test mode it may crash because Firebase is not configured. Stub it in `ServicesContainer` when that happens.
- The debug build prefills the login form; `LoginScreen.replaceText` clears it before typing.

## Android UI tests (Maestro, 2026-11-27)
- **Runner:** Maestro flows in `app/Android/maestro/` (XCUITest can't run on Android; Espresso would mean Kotlin against generated UI). One top-level flow per iOS class (`login`, `customer-list`, `customer-picker`, `pos`, `kirana-pos`), one file per iOS scenario under `scenarios/<flow>/<slug>.yaml`, shared steps (page-object twins) in `common/`.
- **Parity rule:** every iOS `scenario("…")` / `runActivity(named: "…")` needs a Maestro twin. `scripts/check-ui-test-parity.sh` enforces it (37/37 at creation) and runs first in CI. When adding an iOS scenario, add the Maestro file and its `runFlow` line in the same PR. A scenario that can't run on Android keeps its file with first line `# android-skip: <reason>`.
- **Test-mode flags:** `UITestingConfig` reads `ProcessInfo.arguments`, which Android never fills. Maestro `launchApp.arguments` arrive as intent extras; `MainActivity.exportUITestingExtras` (Main.kt) copies `UITesting`/`UITestingSeed` into env vars `APOORVA_UITESTING`/`APOORVA_UITESTING_SEED`, which `UITestingConfig` reads under `#if os(Android)`. Env vars (not UserDefaults) because native Swift and Kotlin share the process env, and nothing persists. Works because `AppCoordinator.instance` and the `ServicesContainer` lazies are first touched after the activity starts; `onInit` (Application) still configures Firebase on Android, which is harmless.
- **Reset:** every scenario relaunches with `clearState: true` (the seeder also clears and reseeds), instead of the iOS in-app `resetToEmptyBill`/`resetPicker` helpers. Slower (one launch + seed per scenario) but deterministic. iOS mid-scenario resets map to relaunches too.
- **Selectors:** root `Box` in Main.kt sets `testTagsAsResourceId = true` so `accessibilityIdentifier` (Compose `testTag`) matches Maestro `id:`. iOS label predicates map to regex `text:` (e.g. `"Meena S, .*"`). iOS `BackButton` / sheet Close / "Keep billing" map to the system `back`.
- **Runner script:** `scripts/android-ui-test.sh [flow] [apk]` (needs adb + maestro and a running x86_64 emulator; DEBUG APK only).
- **CI:** `.github/workflows/android-ui-tests.yml`: parity check, then a macOS job builds `skip export --debug --arch x86_64`, then an ubuntu job (KVM, `reactivecircus/android-emulator-runner`, API 34) runs Maestro and uploads results on failure. `ci.yml` calls it on push to main only; `workflow_dispatch` takes an optional `flow`.
- **Unverified at creation (no local emulator/maestro, no-build rule):** that SkipUI renders `accessibilityIdentifier` as `testTag`; how Android merges row labels (regex text selectors may need tuning); the `skip export --debug` flag and that Swift `DEBUG` is set in Skip's Android debug build. Expect the first CI run to need selector fixes.
- Post-login assertion is "sign-in button disappears"; tighten it once a stable home-screen identifier exists.
